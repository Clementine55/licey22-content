# licey22-content

Обходит старый сайт лицея (Nubex), сохраняет содержимое каждой страницы в
`pages_content/` (JSON + Markdown) и публикует результат в GitHub — так,
чтобы у каждой страницы был постоянный, не меняющийся между запусками URL.

## Как устроено

```
config.py              — все настройки и пути в одном месте
utils.py                — now(), load_json/save_json
http_client.py          — скачивание страниц (с кэшем HTML и одним повтором при сбое)
links.py                — "красивые" URL, email-обфускация (state/link_map.json, state/emails_map.json)
crawler.py               — обход раздела сайта по ссылкам (BFS)
content_extractor.py     — разбор HTML в блоки: заголовки, абзацы, списки, таблицы, файлы
markdown_export.py       — рендер блоков в Markdown
state.py                 — хэш содержимого страниц (state/page_state.json)
page_content_parser.py   — точка входа: обходит сайт, парсит, пишет файлы
publish_to_github.py     — запускает парсер и коммитит/пушит результат в git

pages_content/           — контент сайта (то, что публикуется) — .json + .md на страницу
state/                    — служебные файлы парсера, см. раздел "Файлы состояния" ниже
```

Python-файлы намеренно лежат плоско, в одной папке — их 11 и они активно
зависят друг от друга (например, `content_extractor.py` дёргает
`links.resolve_url`), раскладывать по под-папкам ради 11 файлов смысла
пока нет: пришлось бы либо превращать всё в пакет с `__init__.py` и менять
импорты, либо возиться с `sys.path` — а `publish_to_github.py` при этом
запускает `page_content_parser.py` просто по имени файла. Если код
вырастет в разы — тогда стоит выделить, например, `parser/` под модули.
А вот данные (`pages_content/` и `state/`) — не код, и на них это
соображение не распространяется, поэтому они в отдельных папках.


## Запуск

Разобрать сайт заново, ничего никуда не публикуя:

```bash
python3 page_content_parser.py
```

Разобрать сайт и запушить изменения в GitHub:

```bash
python3 publish_to_github.py
```

`publish_to_github.py` сам запускает `page_content_parser.py` (и
`apply_link_map.py`, если он лежит рядом), затем делает `git add -A`,
коммит и `git push`. Если запушить не получилось (сеть) — коммит остаётся
локально и уйдёт при следующем запуске.

Для ежедневного автообновления — в crontab:

```
0 3 * * * cd /path/to/licey22-content && ./.venv/bin/python publish_to_github.py >> publish.log 2>&1
```

## Почему парсер не пропускает "неизменившиеся" страницы

Раньше решение "разбирать страницу заново или нет" принималось по хэшу
сырого HTML. Это ломалось на старом сайте: в HTML рядом с реальным текстом
сидит технический шум, который меняется от запроса к запросу (счётчики,
токены форм, версии статики в `?v=...`). Из-за этого хэш "прыгал" даже
когда видимое содержимое не менялось, и `git diff` показывал изменения
на всех страницах сразу.

Поэтому сейчас:

- страница **разбирается всегда** — сеть и CPU дешёвые;
- хэш (`state.blocks_hash`) считается **после** `extract_blocks()`, то есть
  от уже очищенного содержимого (заголовки/тексты/файлы), а не от сырого
  HTML — шум туда просто не попадает;
- этот хэш решает только одно: перезаписывать ли `.json`/`.md` на диске
  (а значит — попадёт ли страница в коммит).

## Один HTTP-запрос на страницу, а не два

Обход сайта (`crawler.discover_section_pages`) и разбор контента
(`page_content_parser.parse_page`) раньше независимо скачивали каждую
страницу — обход, чтобы найти ссылки, разбор, чтобы получить блоки.
Итог: 78 страниц превращались в ~156 HTTP-запросов за прогон, хотя нужный
HTML уже был в руках после обхода.

Теперь `http_client.fetch()` кладёт скачанный HTML в кэш в памяти
(`_html_cache`), а `parse_page()` сначала проверяет кэш и лезет в сеть,
только если там пусто (что бывает лишь в редких крайних случаях). Кэш
живёт один прогон и не пишется на диск.

## Устаревшие страницы

Если раздел на старом сайте исчез или переехал, его `.json`/`.md` в
`pages_content/` не остаются висеть вечно: в конце каждого прогона
`page_content_parser.py` сверяет список файлов на диске со списком страниц,
реально найденных при обходе, и удаляет всё лишнее (заодно чистит и
`page_state.json` от таких записей).

## Файлы состояния

Лежат в папке `state/` (не в `pages_content/` — это внутренняя бухгалтерия
парсера, а не контент сайта). Создаются и обновляются автоматически, в
репозитории не нужно их создавать руками:

| Файл                      | Что хранит                                              |
|---------------------------|------------------------------------------------------------|
| `state/page_state.json`   | хэш содержимого каждой страницы (см. выше)               |
| `state/link_map.json`     | соответствие "сырой URL старого сайта → красивый путь"    |
| `state/emails_map.json`   | расшифровка email-картинок (см. ниже) |

Если раньше эти файлы лежали прямо в корне репозитория (старая раскладка) —
при первом же запуске они автоматически переедут в `state/`, руками
ничего двигать не нужно (см. `config._migrate_legacy_file`).

`pages_content/_toc.json` — сводное оглавление по всем страницам
(заголовок, slug, список подзаголовков, число прикреплённых файлов).

### Про `emails_map.json` и «НЕИЗВЕСТНАЯ ПОЧТА»

Старый сайт (Nubex) рисует адреса почты картинкой — специально, чтобы их
нельзя было автоматически вытащить из HTML. Программно расшифровать это
нельзя: параметр вида `?p=JydZAHlWVBZbWlhDTA==` — не просто закодированный
адрес, а нечитаемая внутренняя штука движка.

Когда парсер встречает такую картинку впервые, он:
1. заводит в `state/emails_map.json` пустую запись с этим ключом;
2. в тексте страницы вместо адреса пишет `[НЕИЗВЕСТНАЯ ПОЧТА: ?p=...]`.

Чтобы починить конкретный адрес:
1. Открыть исходную страницу на старом сайте, посмотреть на картинку
   глазами и прочитать адрес.
2. Найти в `state/emails_map.json` этот ключ и вписать туда адрес:
   ```json
   "?p=JydZAHlWVBZbWlhDTA==": "priemnaya@licey22.ru"
   ```
3. Запустить парсер ещё раз — адрес подставится, а страница попадёт в
   коммит (её содержимое реально изменилось).
